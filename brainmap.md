# brainmap.md — FabVidEdit

## Base et chemins
- Base technique `0cb6d330a88d8d654f4e5bc9edd50e5a523887d4` / branche `agent/v0.25-matrix-texture-preview`. Le dépôt distinct FabCut possède une version 0.4 ; ne pas amalgamer les historiques.
- `app/src/main/java/com/fabvidedit/app/ui/EditorScreen.kt` : Compose, `CompositionPlayer`, `PreviewSurface`, `ExportOptionsDialog` et `ExportChoiceRow`. L'UI fournit un `ExportSettings` complet au ViewModel. `remember` préserve le geste pendant les changements de transform. La composition d'aperçu utilise une résolution plafonnée et 30 i/s, distincte de l'export.
- `FabVidEditViewModel.kt` : `startExport(ExportSettings)` vers `ExportManager.start` ; ancien overload `startExport(Int)` maintenu pour compatibilité, ne plus l'utiliser dans la nouvelle UI.
- `media/VideoEncoderCapabilities.kt` : MediaCodecList / MediaCodecInfo, filtre encodeur matériel HEVC. Information déclarative du constructeur, ne garantit pas toutes résolutions et cadences.
- `media/ExportManager.kt` : état d'export, proxy TS local MP4/MKV, préflight stockage, mime H.264/H.265 et AAC, bitrate vers `VideoEncoderSettings`, fps/résolution vers `CompositionFactory.create` ; les proxies sont dédupliqués par URI pour l'export courant, puis supprimés.
- `media/CompositionFactory.kt` : même composition d'effets pour lecture et export, avec `Presentation.createForShortSide` optionnel en preview/export. `AnimatedTransformEffect` applique les matrices ; les effets globaux de texte et les pistes visuelles restent à confronter au rendu réel.
- `media/IncomingMediaResolver.kt` : `ensureOwnedClone` réutilise un fichier app-owned déjà durable ; les URI externes sont clonées. `MediaImportPipeline.importContainer` efface seulement son clone temporaire `incoming/` en finally.
- `media/StreamSourceMaterializer.kt` : scan de changements de résolution, séparation sans réencodage des streams, écritures `streams/<containerId>`, budget d'espace. Cette étape reste coûteuse sur grands conteneurs, non remplacée.
- `media/LocalFfmpegInput.kt` : chemins directs pour sources détenues par l'app et fichiers locaux ; copie temporaire pour content:// externes.
- `media/TimelineThumbnailCache.kt`, `TimelineWaveformCache.kt` : caches disque bornés JPEG 96 MiB et onde 64 MiB ; pas encore de preuve de bon comportement sur grands médias réels.
- `app/build.gradle.kts` : version 0.25.1, ARM64 ; `.github/workflows/android.yml` : tests, lint, APK et AAB debug nommés ; publication de ces deux binaires par `gh release create --prerelease` depuis le runner de branche de correction seulement. Le quota `actions/upload-artifact` est saturé, les upload-artifact ont été retirés. Aucun push d'APK lourd dans les fichiers du dépôt ; la release peut échouer indépendamment d'un build réussi.

- FABVID-EXP-001 : ancien dialog `onExport(Int)` → overload qui reconstruit `ExportSettings(resolution=…)` → choix codec/fps/débit de l'UI perdus. Le dialog doit passer `ExportSettings` complet. Test du comportement à effectuer sur téléphone.
- FABVID-PRV-001 : `remember(transform)` effaçait potentiellement le geste quand le transform changeait pendant celui-ci ; reconstruction à `project.updatedAt` reste sensible. L'allègement 720/480 ne résout pas à lui seul tout incident de rendu.

## FABVID-LRG-002 — parcours d'import corrigé dans v0.25.2
1. `FabVidEditViewModel.createProject/addClips` : `cleanupOrphans` via `withContext(Dispatchers.IO)`, message occupé actualisé par callback, `finally` remet `_busyMessage` à null même sur exception Kotlin. `importContainers` relie le callback.
2. `MediaImportPipeline.importContainer` : distingue fichier déjà app-owned et clone entrant jetable ; un fichier possédé par le projet n'est jamais supprimé au nettoyage de l'import. Signale étapes copie/inventaire/scanner/extraction.
3. `IncomingMediaResolver.copyIntoProjectStorage` : copie des octets avec tampon 256 KiB ; un URI externe soumis à permission temporaire nécessite toujours une copie locale ; pas de stockage des octets vidéo entiers en RAM.
4. `StreamSourceMaterializer.split` : transmet dossier temporaire au scanner et message d'étape, puis extrait pistes en `-c copy` et `-map` ; pas de `+faststart` sur copies MP4 temporaires. La séparation de flux reste sur disque et peut occuper le volume d'origine ou davantage.
5. `ResolutionFrameScanner.scanInput` : FFprobe `-skip_frame nokey -show_frames ... -o fichier`. Sortie native vers fichier textuel local, max vérifié 64 MiB ; premiere passe `forEachLine` histogramme <=32 géométries/stream, deuxième passe `useLines` et automate de changements <=256 segments avant coalescence <=24 ; mémoire O(nombre de pistes + géométries + segments), pas O(nombre d'images). Fichier supprimé en `finally` ; si échec, repli vers les propriétés de stream. Limite connue : changements sans image-clé/codec ignorant skip_frame peuvent ne pas être reconnus ; valeur d'origine conservée et tests réels nécessaires.
6. `CapCutMultitrackEditorV06` : véritable interface multipiste utilisée par `FabVidEditApp`. Le `CompositionPlayer` passe maintenant 720p/30 ou 480p/30 (low RAM) à `CompositionFactory`; son lecteur de secours `ExoPlayer` reste à auditer pour les gros fichiers. Dialog export multi-piste H264 par défaut, HEVC seulement si encodeur matériel détecté.
7. `ResolutionFrameScannerTest` : vérification JVM du parseur compact et des données invalides ; essais FFprobe natif sur Android et comparaisons sur vidéos à résolutions variables non couverts.
8. `.github/workflows/android.yml` : build v0.25.2 + publication prerelease APK/AAB pour contourner quota Actions ; aucune garantie de release tant que CI non vérifiée.

## AUDIT v0.0.5 sans modification du moteur — PREVIEW-012 / EXPORT-SMALL-013 (23/09/2026)
Source de vérité : HEAD `3cef251b07a9228b507b4e198e4d012ac1e2d6c1`, Release v0.0.5. Chemin simplifié : `CapCutMultitrackEditorV06` → fallback ExoPlayer pour une piste → `currentPositionMs` piloté par `LaunchedEffect(player,fallbackPlayer,stablePreview,fallbackClip?.id)`, `delay(80L)`, `SystemClock.elapsedRealtime` → `fallbackVisual = v020FallbackVisual(project, clip, currentPositionMs, directPreviewTransform)` → recomposition `AndroidView.update` → `FabVidVideoTextureView.bind()` + `applyPreviewTransform` → allocation `Matrix`/ `PreviewCanvasGeometry.forFrame`/ `TextureView.setTransform` → invalidation de vue ; `graphicsLayer` alpha → cadence visible. La boucle est aussi reliée à selection/keyframes, timeline (règle, slider), audio volumes et recalcul des filtres/lists. Une boucle de 80 ms ne rafraîchit directement l'animation des keyframes d'UI qu'environ 12,5 fois/s, même si le décodeur vidéo peut produire d'autres images entre deux itérations. Ne pas confondre cadence image réelle et cadence contrôle UI.
Autres suspects à instrumenter : `LaunchedEffect(project.updatedAt,...,stablePreview,selectedClip?.timelineTrackIndex)` relance `syncFallback` + `syncStableAudio` (seek vidéo et deux lecteurs son) à chaque modification de projet/piste/preview ; `fallbackClip?.id` annule et relance la boucle de temps lors d'un changement de piste ; `syncFallback` fait prepare+seek quand clip change ; `onSurfaceTextureSizeChanged` refait `bind(wanted)` qui peut unbind/rebind avec nouveau `Size` lors d'une modification du layout (inspecteur), interrompant la surface/le décodeur. `TextureView` a un coût d'intégration à la hiérarchie Android, significatif sur gros décodage/zoom ; aucune preuve actuelle que la matrice seule ou le CPU soit responsable. `CompositionPlayer` multipiste et son propre graph sont une autre voie à profiler séparément (utilisateur observe « aperçu simplifié »).
